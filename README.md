# UPI Fraud Detection Dashboard

An end-to-end data analytics project: a synthetic UPI (Unified Payments
Interface) transaction dataset with documented fraud patterns injected, an
**explainable rule-based risk engine** that scores every transaction, a set of
DuckDB SQL investigation queries, and a Streamlit dashboard with a case
review queue.

**Live demo:** _coming soon — link will be added here once deployed to
Streamlit Community Cloud._

> ### ⚠️ Synthetic data — honesty note
> Every transaction in this project is **synthetic**, generated by a seeded
> script (`src/generate_data.py`, seed 42). No real transactions, people,
> accounts or VPAs are involved. VPAs are masked by construction
> (e.g. `ra•••@okhdfcbank`). Fraud labels exist only because the fraud was
> deliberately injected as documented patterns — which is exactly what makes
> it possible to *measure* how well the detection rules work. Performance
> numbers below describe this synthetic dataset, not real-world UPI fraud.

## What the dashboard shows

- **KPI row** — total transactions, labelled fraud rate, value at risk
  (₹ value of High + Critical transactions), flagged-for-review count, and
  rule recall @ High+
- **Fraud-rate heatmap** by hour × weekday, **daily trend** of volume vs
  fraud, **amount distribution** (fraud vs genuine), **fraud by pattern**,
  and a **risk-band chart** showing how labelled-fraud rate climbs by band
- **Top risky receivers** table and a **Case Review Queue** (High + Critical,
  worst first) where every case shows the human-readable reasons it was
  flagged, plus a per-transaction inspector
- Sidebar filters: date range, transaction type, risk band, fraud pattern

## Quickstart

```bash
pip install -r requirements.txt
python -m src.generate_data     # writes data/transactions.csv (40,000 rows)
streamlit run app.py            # dashboard on http://localhost:8501
pytest                          # 18 tests
```

If `data/transactions.csv` is missing, the app generates it on first load —
that is what makes the one-click Streamlit Cloud deploy work.

## The data

40,000 transactions over 30 days (2026-10-14 → 2026-11-12), from 3,000
synthetic sender accounts and 1,200 receivers. Genuine amounts are lognormal
(median ₹450, 99th percentile ≈ ₹5,331); ~96% of transactions succeed.

### Data dictionary

| Column | Meaning |
|---|---|
| `txn_id` | 12-digit UTR-style synthetic reference |
| `timestamp` | Transaction time |
| `amount_inr` | Amount in Indian Rupees |
| `txn_type` | `P2P` (person→person) or `P2M` (person→merchant) |
| `sender_vpa` / `receiver_vpa` | **Masked** Virtual Payment Address, e.g. `ra•••@okhdfcbank` |
| `sender_key` / `receiver_key` | Full synthetic account identity — the analytics key (see Methodology) |
| `sender_bank` | Sender's bank |
| `device_id` | Device the payment was initiated from |
| `is_new_device` | True if the device was never seen before for this sender |
| `city` | Sender's city (Indian metros + tier-2) |
| `status` | `SUCCESS` / `FAILED` — some fraud rows fail (blocked attempts) |
| `is_fraud` | Ground-truth label (knowable only because the data is synthetic) |
| `fraud_pattern` | Which injected pattern produced the row (blank if genuine) |
| `risk_score`, `risk_band`, `risk_reasons` | Added by the rule engine in `src/risk.py` |

### Injected fraud patterns (664 rows, 1.66% of volume)

| Pattern | Rows | ₹ value | How it behaves |
|---|---:|---:|---|
| `velocity` | 226 | ₹19.6 lakh | One sender fires 6–12 transactions within 10 minutes, at elevated amounts |
| `odd_hour` | 114 | ₹13.8 lakh | Bursts of 4–6 transactions between 00:00–04:00 |
| `micro_testing` | 112 | ₹10.2 lakh | 4–5 tiny round amounts (₹1–₹100) then one large transfer, all inside ~10 minutes |
| `mule_fan_in` | 87 | ₹7.8 lakh | One receiver collects from 11–15 unique senders in a day |
| `mule_fan_out` | 75 | ₹8.2 lakh | One sender pays 11–14 unique receivers within an hour |
| `new_device_high_value` | 50 | ₹28.2 lakh | First-seen device + single transfer of ₹21,000–₹95,000 |

## Risk rules (explainable, deterministic)

Every rule that fires adds points and a written reason — an analyst can
always see *why* a transaction was flagged. Scores cap at 100.
Bands: **Low** < 25 · **Medium** 25–49 · **High** 50–74 · **Critical** ≥ 75.

| Rule | Points | Trigger |
|---|---:|---|
| `velocity_10min` | +40 | ≥5 transactions from the same sender inside any 10-minute window |
| `new_device_high_value` | +35 | First-seen device and amount above ₹20,000 |
| `receiver_fan_in` | +30 | Receiver collected from ≥8 unique senders on the same day |
| `sender_fan_out` | +30 | Sender paid ≥8 unique receivers within one hour |
| `micro_testing` | +25 | Transfer > ₹5,000 after ≥3 tiny (≤ ₹100) transfers from the same sender within the prior hour |
| `high_amount` | +20 | Amount ≥ 99th percentile of genuine amounts (≈ ₹5,331 here) |
| `odd_hour` | +15 | Transaction hour between 00:00 and 04:00 |

### Measured rule performance (this dataset, computed — not asserted)

| Metric | Value |
|---|---:|
| Labelled fraud | 664 of 40,000 (1.66%), worth ₹87.7 lakh of ₹3.97 crore total |
| Flagged High + Critical | 412 transactions (1.03% of volume) |
| **Recall @ High+** | **62.0%** (412 of 664 fraud rows caught) |
| **Precision @ High+** | **100.0%** (every flagged transaction is labelled fraud) |
| Value at risk in queue | ₹78.97 lakh |

Recall by pattern: `new_device_high_value` 100% · `mule_fan_out` 83% ·
`odd_hour` 83% · `mule_fan_in` 78% · `velocity` 52% · `micro_testing` 18%.

The honest weak spots are instructive: about half of velocity bursts sit at
exactly 40 points (Medium) when their amounts don't also trip the
high-amount rule, and micro-testing *probes* are individually almost
invisible (a ₹10 transfer looks harmless) — the sequence is caught at the
large cash-out transfer (those reach Critical), which is why pattern-level
recall is 18% while the money-weighted catch is much better. Precision of
100% is partly an artefact of synthetic data: genuine behaviour here is
well-behaved by construction, so rules rarely misfire. Real queues trade
much lower precision for recall.

## SQL investigation queries

`sql/fraud_queries.sql` contains 7 commented DuckDB queries over the raw CSV,
each headed by the business question it answers: overall fraud rate; fraud
rate by hour; daily trend; top receivers by fraud value; velocity suspects
(self-join); fan-in receivers; high-value transfers from new devices.
Run them with `duckdb -c ".read sql/fraud_queries.sql"` or any DuckDB client.

## Methodology

- **Seeded generation (seed 42)** makes the dataset — and every number in
  this README — exactly reproducible.
- **Identity vs display.** Behavioural rules group by `sender_key` /
  `receiver_key` (full synthetic identity), never by the masked VPA: ~186
  distinct masked sender strings represent 3,000 accounts, so grouping by
  the masked value would fabricate velocity and fan-in signals. A regression
  test (`test_masked_vpa_collisions_do_not_fabricate_velocity`) locks this in.
- **Patterns are injected as intact sequences** (never row-sampled), because
  dropping individual rows would decapitate the bursts the rules detect.
- **Fraud pattern amounts are elevated relative to genuine medians** — part
  of the pattern definitions, since draining or moving money is the point of
  the fraud; rule stacking (e.g. velocity + high-amount) is what pushes most
  pattern rows over the High threshold.
- Some fraud rows are marked `FAILED` — blocked attempts are part of real
  fraud telemetry.

## Limitations

- **Synthetic data.** Real UPI fraud is messier, adversarial and adaptive;
  these patterns are deliberately overt so rule performance can be measured
  against ground truth. Nothing here estimates real-world detection rates.
- **Rules, not ML.** A transparent heuristic ruleset is a feature for
  explainability and a limitation for subtle fraud.
- **Labels are injected patterns only.** "Genuine" rows are clean by
  construction; real datasets hide unlabelled fraud in the negatives, which
  is why real-world precision/recall would both be lower.
- **Small universe.** 3,000 senders over 30 days means genuine behavioural
  collisions (e.g. a popular merchant tripping fan-in) are rarer than at
  production scale.

## Future work

## Tests

18 pytest tests cover: generation reproducibility and fraud-rate range;
every pattern present; no unmasked VPAs; each of the 7 rules firing on
crafted frames; score cap and band boundaries; the masked-identity
regression; analysis KPIs against hand-computed fixture values; case-queue
ordering; DuckDB executing the investigation queries; and end-to-end rule
performance on the generated data (recall @ High+ ≥ 0.5, flagged < 5%).
